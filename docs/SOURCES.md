## E. What is fact vs inference in this plugin

**Directly source-backed DSH facts:** mid-turn Assistant messages are real session/UI material; visible text and reasoning are separate blocks; tool execution follows Assistant settlement; `ctx.tools.guard()` is a monotonic policy point; `additionalContexts` is model-facing; `agent/turn-stopping` may steer; optional services should use `ctx.get()`; synchronous Session history readers are deprecated by upstream policy for new production code (a prohibition, not a removal: the methods are still public and still used inside `dsh-session`).

**Community empirical evidence:** stale TODO update rates, specific UI pain points, steer delays under long blocking waits, and compatibility break reports. Treat these as environment/version observations rather than universal laws.

**Plugin design choices/inferences:** `disclose_progress` as the reset primitive, its compact three-field schema, `reminderAfterCalls = 8`, `maxReminders = 3`, at most one reminder per model step, counting completed top-level ordinary calls, carrying same-step top-level sibling work across a successful checkpoint reset, coarse activity classification, turn-local state, and the absence of a standing prompt section are local policy choices. They are not DSH defaults. Section H lists the contracts the design retains and the evidence for each.

## H. Contracts retained by the current design

ADR-0007 keeps model-authored disclosure but moves it from Assistant prose to the structured `disclose_progress` tool.

| Dependency | Evidence and consequence |
|---|---|
| Typed model tool registration | The tool-authoring contract exposes `defineTool()`, validated parameter schemas, canonical output, and pure rendering. The plugin uses exactly three required strings and canonical `null` output. |
| Tool schemas are model-facing fixed context | The tools README states that models see permitted tool names, descriptions, and parameter schemas. This is why the declaration is deliberately compact and tested for serialized size. |
| PTC turns ordinary tools into SDK bindings | The tools README documents `mode: ptc`: only `run_code` is direct, while visible tools become generated SDK bindings. A nested progress call therefore has to reset accounting correctly. |
| PTC dispatch children are presentable | `dsh-client-ui-tool` renders the root and PTC dispatch children, then sends atomic calls through normal tool-view slots. The supervisor can inspect a nested progress call without injecting a duplicate model message. |
| Soft reminders can be appended | `tools/post-execute` supports `additionalContexts` and the agent loop delivers them at the next model step. |
| Nested executions are identifiable | `ToolExecution.parent` marks nested PTC dispatches. Ordinary nested calls affect activity but not cadence; nested progress calls still reset the interval. |
| Assistant step identity is durable before tools run | `assistant/message.data.step` is committed before dispatching that response's tool calls. The adapter uses the step number only to prevent several parallel reminders from being delivered before the model can react. |
| Guards and stop steering are unnecessary | `ctx.tools.guard()` is a deny mechanism and `agent/turn-stopping` can force an extra step. The structured progress action eliminates the need for either. |

The fixed cadence, budget, activity window, compact schema, and size ceilings are local policy rather than DSH defaults.

## I. Historical Assistant-text disclosure design (superseded 2026-09-26)

[ADR-0005](adr/0005-structural-disclosure-recognition.md) records the former four-line Assistant-text recognizer. ADR-0007 supersedes it for runtime behavior after a real session showed that a recognized progress response could legally terminate the turn. The helpers remain exported only for compatibility.

- **Local code evidence:** the pre-ADR-0005 predicate accepted any non-whitespace model text.
